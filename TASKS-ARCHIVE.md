## T115 — Licences: the software, the data, and everything linked into the binary

**Category:** release · **Status:** done 2026-09-05

Three files, because three different things ship together under three different
terms, and one `LICENSE` would have been wrong about two of them:

- **`LICENSE`** — a beta evaluation licence. Free use including commercial, no
  redistribution, not open source. Says explicitly that publishing the source
  on GitHub grants nothing, which matters because the repo was already public
  with no licence at all (= all rights reserved, undocumented). Carries three
  clauses a template would not: the beta may produce wrong numbers and its
  terms end at 1.0; nothing it outputs is investment advice; liability
  expressly covers trading losses.
- **`DATA-LICENSE.md`** — the bundled database, and deliberately more
  restrictive than the software. Per-source terms, traced from the loaders:
  Yahoo (no redistribution — the binding constraint), Alpha Vantage (ToS),
  **Wikipedia CC BY-SA 4.0 for `index_membership` — attribution AND
  share-alike**, SEC EDGAR (public domain), FRED, Ken French (Dartmouth) and
  Shiller (Yale). Also carries the defect inventory: survivor-only universe,
  273 unusable series, adjusted-not-traded prices, benchmark/CPI lag.
- **`THIRD-PARTY-NOTICES.txt`** — generated by `gen_notices.py` from
  `go list -deps` and `npm ls --omit=dev`, so it lists what is actually linked
  and bundled: 22 Go modules, 11 npm packages, plus the DuckDB C++ library as
  its own entry (statically linked by `go-duckdb` under a separate Stichting
  DuckDB Foundation copyright). All permissive; every one requires its notice
  to travel with the binary, which was not happening.

**Left for the user:** the copyright line says `IronWarden`, where a legal name
belongs; and the Yahoo redistribution question plus the Wikipedia share-alike
obligation are the two worth a lawyer's ten minutes before a public download

## Factor screening — T108–T111

Added 2026-08-30 from the request: *"I want to test hypotheses like buying
stocks with certain metrics for a given time — ROI/ROE, P/E, B/S and B/A."*

Most of the machinery exists already. T29 dates every reported figure by when
it became public and T33 put `fundamental()` and `market_cap()` in front of a
Lua script, alongside `rank()`, `target_weights()`, `tickers` and `equity()`.
Four things are missing, and they are worth doing in this order: **a figure
that means one thing** (T108), **a way to find out whether a factor ranks
anything before spending a backtest on it** (T109), **a universe instead of a
hand-typed ticker list** (T110), and **the strategy** (T111).

### Stage 0 is yours and comes first — `sec_financials` is not loaded here

Measured against the live database on 2026-08-30:

- Annual fundamentals cover **FY2021–FY2024 only**. 5,375 tickers have exactly
  four annual periods; FY2025 is in for 991 of ~6,400. After the publication
  lag that is about **four portfolio-formation dates in total**.
- Quarterly rows are a *rolling* five-quarter window from yfinance, not
  history. MSFT, XOM and JPM each have quarterly data from 2024-03-31 to
  2025-03-31 and nothing before it. There is no quarterly series to rebalance
  on and no TTM to compute.
- 6,047 tickers have unbroken price coverage 2021-01 → 2026-06, so prices are
  not the constraint. Fundamentals are.

`add_sec_financials.py` fixes all three — 2009 onward, companies that later
died included, and a real `filed` date per row (measured median lag 48 days
against the 90-day worst case the engine falls back to). The Go side
(`LoadSECFundamentals`, and the SEC-first precedence inside
`PointInTimeFundamentals`) is written and waiting for the table.

```bash
python3 add_sec_financials.py --dry-run --limit-quarters 1   # probe
python3 add_sec_financials.py                                # ~20 min, ~7 GB, ~7M rows
```

DuckDB is single-writer: the app must be closed, and the agent must not run
this. Worth doing **before** the real run: `TAG_TO_METRIC`
(`add_sec_financials.py:95`) has no debt tag, so leverage and ROIC are not
reachable from SEC data at all. Adding `LongTermDebtNoncurrent` and
`DebtCurrent` is a two-line change now, or another twenty-minute reload later.

Four formation dates is not a backtest. T109's scan will refuse today's data on
`MinSamples = 12`, and T111 run today produces four bets wearing a strategy's
clothes. That is the honest state of the database, and it is why Stage 0 leads.

## T102 — T100's live check never ran: the app held the database

**Category:** verification · **Status:** done 2026-08-23 — and it was right to
be suspicious. The live run reported `real 0.00%`, the rewrite had NOT fixed
it, and the actual cause was `Portfolio.Clone` dropping the field. See T106.

`RealAnnualReturn` is fully unit-tested — the arithmetic, the refusal to
deflate over a short window, and `GetCPISeries` against a synthetic
`economic_indicators` with the Date column declared as DATE, TIMESTAMP *and*
VARCHAR. What could not be re-run is the end-to-end check against **your**
database, because `wails dev` held the DuckDB write lock for the rest of the
session.

**Why this matters more than usual here.** A wrong query in `GetCPISeries`
returns nil, and nil is indistinguishable from "this database has no CPI table"
at every layer above it. The failure mode is not an error — it is the column
quietly never appearing.

An earlier run *did* report `real 0.00%` for a window CPI covers. That version
used `Date BETWEEN CAST(? AS TIMESTAMP_NS)`, which the rewrite removed: the
reader now takes the whole series (949 rows) and filters in Go, and normalises
the date through `any` so a text column cannot break it. That is very likely
the cause and the cure, but **it was never observed working against the real
table**, so it is recorded as unproven rather than claimed as fixed.

### To close it

Quit the desktop app, then:

```bash
REAL_RUN=1 go test ./ui -run TestRealReturnAgainstTheRealDatabase -v
```

It prints the nominal and real figures for both the portfolio and `$SP500` and
fails if the real return is missing. If it passes, this task is done. If it
still reports `real 0.00%`, the log line it emits — `economic_indicators has no
usable CPIAUCSL rows` versus `querying CPI: <error>` — says which half is
wrong.

## The data-curation programme — T39–T48

**PAUSED 2026-08-17** at the user's request ("let's forgo delisted for now"),
after the measurement that free sources serve no delisted price history: the
price table holds no series ending more than two years ago. T40–T46 shipped and
are useful on their own; T39, T51 and T52 remain `todo` but rank below the
strategy-discovery block above.

Added 2026-08-17 from the request: *"curate the best possible data set I can for
free; delisted stocks should be treated the same as normal stocks in the DB for
backtesting."* These sit above everything else in the queue because every
measurement the app makes is downstream of them.

**Read `analysis/free_data_sources.md` before starting any of them.** It records
what was probed on 2026-08-17 and what each free source actually returns. The
headline: **no free source serves price history for companies that stopped
trading.** Alpha Vantage's free tier lost `outputsize=full`, Stooq's CSV
endpoint is now behind a JavaScript proof-of-work challenge, and Yahoo returns
zero bars for every dead symbol probed (`LEHMQ`, `ENRNQ`, `WAMUQ`, `SIVBQ`,
`SUNEQ`, `BBBYQ`, …). Yahoo is also the *source* of the recycled-series defect:
`BBBY` returns 6,093 bars running to today, and `SUNE` returns 11,275 from 1981,
because two different companies have held each symbol.

So "best possible free data set" means fixing what free data *can* fix, and
bounding the rest honestly rather than pretending it away:

| defect | free fix | task |
|---|---|---|
| 269 tickers are two companies in one series | yes — delist dates (have) + SEC former names | **T39** |
| `company_info` is empty, so no sector data | yes — SEC `sic` per CIK, dead companies included | **T40** |
| nothing knows which series are trustworthy | yes — a quality audit over the price table | **T41** |
| no delisting *reason*, so no honest delisting return | mostly — SEC Form 25 / 15 / 8-K 1.03 | **T42** |
| survivor-only *selection* (who was in the index then) | yes, for one index — dated Wikipedia tables | **T43** |
| `financials` starts 2020-07 and only live tickers | yes — SEC Financial Statement Data Sets, 2009+ | **T44** |
| a series ending mid-window is silently mishandled | yes — engine-side, no new data at all | **T45** |
| no pre-2013 delisted **prices** | **no** — paid feed, or a key-gated free tier | T47, T20 |

Ordering note: T45 is the one that directly answers "treat delisted stocks the
same as normal stocks", and it needs **no new data** — do it early rather than
waiting on the loaders. T39 and T45 together are most of the user-visible value.

Two standing constraints for all of these, from `CLAUDE.md`:

- **The agent writes loaders; the user runs them.** `stock_data.db` is a 2.9 GB
  single-writer file. Every loader below ships with `--dry-run` as its verified
  path, and every consumer must be **inert until its table exists**, so an
  unloaded database produces byte-identical results to today.
- **No new dependencies.** `urllib`, `pandas`, `duckdb` and `yfinance` are
  available; anything else stops the task as blocked. SEC endpoints need a
  `User-Agent: <app> <email>` header (fair-use policy) and a ≤10 req/s cap —
  no key, no signup.

## T100 — Inflation-adjusted (real) returns

**Category:** feature · **Status:** done 2026-08-23 — `RealAnnualReturn` on
`Metrics` and `BenchmarkStats`, `src/data/inflation.go`,
`src/backtest/inflation.go`, **Real %** column in the results table.
**One thing unverified — see T102.**

A 10% annual return in 2021 and a 10% annual return in 2013 are not the same
result, and the app currently reports both as `10.00` under **Annual %**. Show
the real return alongside the nominal one.

### Decided 2026-08-23 — it is a METRIC

Testfolio was looked at for comparison and does it two other ways: a post-run
view toggle that flips the whole result between nominal and real, and a preset
`INFLATION` ticker that plots US CPI as if it were an asset. Both were put to
the user and **both were declined**: the real return belongs in the metrics
table, beside the nominal one, as its own figure.

That settles the two questions that were open below:

- **No config key and no view toggle.** A new column, always computed when CPI
  covers the window.
- **No `$CPI` collection.** It would have been cheap — the `$`-prefixed
  synthetics are exactly that mechanism — but a line on a chart is not the
  number people want to read, and it would have needed a write-mode loader run.

Testfolio's USD deflator is a Shiller-CPI/CPI-U splice reaching 1871. Do not
build that: `CPIAUCSL` alone covers everything the price data can reach, since
the equity history here starts 2006-05-25.

### The data is already there

`economic_indicators(Date, series_id, indicator_name, value)` carries
**`CPIAUCSL`** — CPI for All Urban Consumers, All Items, seasonally adjusted,
the standard FRED deflator. Monthly. The table as a whole spans 1927+; confirm
CPI's own first date before assuming it covers the oldest windows (the DB was
locked when this was written, so that one is unverified).

Two things to know about the series:

- It is **seasonally adjusted**. For point-to-point deflation over a window
  that is not a whole number of years, that is the right choice; `CPIAUCNS`
  would introduce a seasonal artefact at the endpoints.
- The index is 1982-84 = 100. Only ratios matter, so the base is irrelevant.

### The plumbing already has a precedent — use it

Do **not** invent a new path. `data.GetRiskFreeRates(startTime, endTime)` is
loaded once in `runner.go:562` for the union window and threaded into every
worker as `riskFreeRates map[int64]float64` (`runOne`, `GetBacktestingData`,
`applyBenchmarkMetrics`, …). A CPI index wants exactly the same shape: one
query for the union range, a `map` handed down, read-only so it stays safe
across the worker pool.

It is a few hundred monthly rows. The cost is nil.

### The design fork, and the recommendation

**Option A — deflate the reported returns only.** Add real counterparts to the
headline growth figures and leave everything else nominal. One or two new
`Metrics` fields, no change to the equity curve, no trade affected, no existing
number moved.

**Option B — deflate the equity curve itself**, restating every point in
today's money. This changes the chart, and through it max drawdown, std dev,
Sharpe, Sortino, Calmar and the drawdown table.

**Take A.** B is more work and partly wrong: a drawdown is a *nominal*
experience — you watched the account fall 40% — and restating it in real terms
answers a question nobody asked while corrupting the one metric users trust
most. Sharpe is also conventionally quoted on excess-of-risk-free returns,
which already handles the money-cost-of-time question from a different angle;
deflating on top of that double-counts.

If a real equity curve is wanted later, make it a **display toggle** on the
chart, not a change to the stored series.

### Look-ahead: this one is genuinely safe, and that is worth stating

`regime.go` deliberately refuses to use CPI, and `ui/chat.go` warns that
`economic_indicators.Date` is the **period**, not the release — January's CPI
is published in mid-February and revised for years. Do not let that scare this
task into building a publication-lag pipeline it does not need.

The distinction is **decision vs description**:

- A strategy that *trades* on CPI must lag it, or it peeks. That is what
  `regime.go` deferred and what `PointInTimeFundamentals` exists for.
- A real return *reported after the fact* is a description of a finished
  window. Deflating a 2010-2020 run by the CPI we know today is exactly how
  every index provider reports real returns. Nothing in the simulation reads
  it, so nothing can peek.

Say this in the code comment, or the next person will re-litigate it.

The one honest caveat: **CPI is revised**, so the real return for a given
window can change slightly between runs months apart. Worth a sentence in the
README; not worth engineering around.

### The edge case that will actually bite

CPI for a month is published mid-way through the next one, so **a window ending
in the last ~6 weeks has no CPI for its final period.** Decide explicitly:

1. report `—` rather than a number computed from a short deflator, or
2. deflate over the largest sub-window CPI covers and say so.

(1) is safer and matches how `FundamentalCoverage` already renders `—` for "the
run never asked for this" rather than `0.0`. Whatever is chosen, it must not
silently divide by a CPI ratio spanning fewer months than the return does —
that inflates the real return, in the wrong direction, invisibly.

### Arithmetic

Do not deflate daily. CPI is monthly and the engine is daily on a 252-day year;
interpolating within months invents precision the source does not have. Use the
endpoints:

```
inflationFactor = CPI(end) / CPI(start)
realGrowth      = nominalGrowth / inflationFactor
RealAnnualReturn = (realGrowth ^ (1/numYears) - 1) * 100
```

`GetAnnualReturn` (`metrics.go:533`) already computes `nominalGrowth` as the
product of `1+r`; mirror its shape and its `numYears <= 0 -> 0` guard rather
than writing a second convention.

Note this is the correct compounding form. `nominalReturn - inflationRate` is
the approximation, and it drifts meaningfully over decade-long windows, which
is precisely the case this feature is for.

### Definition of done — the parts this repo will punish you for skipping

1. **Adding a field to `backtest.Metrics` breaks the build** unless
   `appReference` in `ui/chat.go` names it.
   `TestSystemPromptDocumentsEveryMetric` (`ui/tools_test.go:179`) reflects
   over every field. Update `leanReference` too — nothing enforces that one.
2. **A new metrics column needs a matching cell in the BENCHMARK row.** This is
   T97, which shipped a row that printed max drawdown under Calmar. The smoke
   check `every table row matches its header` will now catch it, but do not
   make it catch you.
3. **`BenchmarkStats` carries only four figures.** Either give the benchmark a
   real return too (it has the same start/end, so the same CPI ratio applies —
   cheap and genuinely useful: "the index returned 7% real, you returned 4%")
   or emit `—`. Prefer the former; comparing real-to-nominal across the two
   rows would be the worst outcome.
4. **`[Output] fields`** in `reporter.go` — decide whether the new metric is
   selectable and sortable. T63 and T64 are the precedent; a field the reporter
   does not know about is a filter expression that fails at runtime.
5. **README.md**, in the metrics table.
6. **No config key should be needed.** This adds a column, it does not change a
   simulation, so nothing defaults to anything and every existing config keeps
   producing identical numbers. If a knob does turn out to be needed, its zero
   value must reproduce today's output exactly.

### Naming

`RealAnnualReturn` reads better than `InflationAdjustedReturn` and matches the
existing `AnnualReturn`. The UI column wants to be **Real %** next to
**Annual %** — adjacent, so the comparison is the point.

### Settled

Cumulative inflation over the window was offered as an extra figure and
**declined** 2026-08-23. The headline real return is the whole ask.

## T104 — Four reported metrics were silently zeroed on every real run

**Category:** bug · **Status:** done 2026-08-23 — `metrics.go`, found while
doing T101

`GetBacktestingData` ends by assigning a freshly built `Metrics` struct:

```go
metrics := Metrics{ ... }   // everything DERIVED from the return series
p.Metrics = metrics         // <- wholesale overwrite
```

Four fields are not derived, they are **accumulated during the simulation**,
and the assignment threw all of them away:

| field | counted by |
|---|---|
| `BorrowPaid` | `chargeBorrow`, once per day per short |
| `MarginCalls` | `enforceMaintenanceMargin` |
| `DelistedHoldings` | `applyDelistingReturns` — which runs on the line *before* the overwrite |
| `UnclassifiedDelistings` | same |

Measured, not inferred: a short with `borrow_bps_annual = 500` had
`BorrowPaid = 0.992` before the rebuild and **`0` after**.

So every real run has reported zero borrow paid, zero margin calls and zero
delisted holdings, for as long as each has existed — while `README.md`,
`CLAUDE.md` and both assistant prompts describe them as reported figures.

### Why nothing caught it

The tests for those fields set them up and assert them **without ever calling
`GetBacktestingData`** (`short_test.go` drives the margin path by hand). They
pass, and they always would have. The overwrite only happens on the real path.

### Fixed

The accumulated fields are now carried across the rebuild explicitly, with a
comment saying that anything counted in the loop belongs in that list.
`TestAccumulatedMetricsSurviveTheRebuild` sets every one of them to a
recognisable value, calls `GetBacktestingData`, and checks they survive.

### What this changes for you

**Numbers move — upward, for configs that were affected.** Any run using
`AllowShort` with a borrow rate now reports the borrow it actually paid instead
of 0; runs that hit a margin call or held a delisted company now report those
too. Nothing else moves: long-only runs with no delistings were already
correct, because all four fields were genuinely 0 for them.

## T101 — Recurring deposits and withdrawals

**Category:** feature · **Status:** done 2026-08-23 — all of A–J, in three
commits: the engine, the buy-and-hold reinvestment, and the surfaces.
`src/backtest/cashflow.go`, `[portfolio.Cashflow]`, `Metrics.NetContributions`
/ `WithdrawalsMissed`, the Contributed / Missed W/D columns, and the
Deposit/Withdraw + amount + frequency controls on the Portfolio card.

**Not done, deliberately:** money-weighted return (IRR), which was scoped out
below and is a different calculation rather than a variant of this one.

Let a portfolio contribute or withdraw on a schedule — £500 a month in, or 4% a
year out. Contributing is how people actually invest, and a decumulation
backtest is unanswerable without withdrawals.

**This task is the explicit authorisation to change the TOML schema** that
`CLAUDE.md` otherwise forbids. Nothing else here is.

`Portfolio.Deposit` and `Portfolio.Withdraw` already exist
(`portfolio.go:381`, `:385`) and are unused — the complete-but-unused methods
the protocol says to keep. This is what they were for.

### Where it goes

`runner.go:344`. The loop today reads:

```go
for day := 1; day < dataLen; day++ {
    p.chargeBorrow()                  // before the strategy acts
    p.Strategy.Step(p, windowed, day)
    p.enforceMaintenanceMargin(windowed, day)
    curr := p.GetPortfolioValue(p.Tickers, windowed, day)
    p.AdjustPortfolioParameters(p.Tickers, windowed, day, prev, curr)
    prev = curr
}
```

A cashflow belongs next to `chargeBorrow()` — before the strategy acts, so the
strategy can see and invest the money on the day it arrives.

### Hazard 1 — a contribution is not a return, and today it would look like one

`AdjustPortfolioParameters` (`portfolio.go:688`) computes

```go
dailyChange = (endingValue - startingValue) / startingValue
```

`prev` is the previous close. Deposit £500 into a £10,000 book and the day
posts a **5% return** the market never delivered. Every metric downstream is
built from `DailyReturns` — CAGR, Sharpe, Sortino, std dev, the rolling
Sharpe, the significance nulls — so all of them inherit it.

The fix is one line, in the right place: after applying the flow, raise the
baseline by the same amount.

```go
flow := p.applyCashflow(date)   // signed; 0 when nothing is due
prev += flow                    // a contribution is not performance
```

That is the standard time-weighted treatment, and it makes the reported return
answer "how did the STRATEGY do", which is the only question a backtest can
answer about a portfolio whose size the user was changing by hand.

**Contrast with `chargeBorrow`, deliberately.** Borrow cost *should* depress
the day's return — it is a real cost of the position. A deposit should not
raise it. The two sit on the same line of the loop and need opposite
treatment; say so in the comment or someone will "fix" one to match the other.

### Hazard 2 — drawdown is computed on raw values, so a withdrawal looks like a crash

`GetMaxDrawdown` and `GetDrawdowns` both read `p.PortfolioCloseValues`, which is
the **raw** book value. Neutralising `DailyReturns` does not touch it. So:

- a withdrawal shows up as a drawdown that never happened;
- a deposit refills the peak and **erases** a drawdown that did.

Max DD, the Calmar ratio, `LongestUnderwaterDays` and the whole Deepest
Drawdowns panel are all wrong in a way that looks entirely plausible.

The fix is to derive drawdowns from a flow-adjusted **index** — compound the
neutralised `DailyReturns` into a series starting at 1.0 — rather than from the
cash value. `rebasedCurve` in `metrics.go:463` already does exactly this
compounding for the benchmark; reuse it rather than writing a second one.

Keep `PortfolioCloseValues` as the real money, because the equity chart should
show the account actually growing when money is added. Two series, two
questions: **what the account was worth** and **how the strategy performed**.
The chart wants the first, every ratio wants the second.

### Hazard 3 — profit becomes a lie

`ResultsView.tsx:102` and `:495` compute profit as `finalValue - initialCapital`.
Contribute £500 a month for ten years and that reports £60,000 of "profit" that
was deposits. Needs `Metrics.NetContributions` (signed, deposits positive), and
profit becomes `finalValue - initialCapital - netContributions`, in the
portfolio row **and** the benchmark row.

### Hazard 4 — the default strategy will not spend the money

**Read this before estimating the work.** `BuyAndHold.Step` (`strategy.go:179`)
opens with `if day != 0 { return }`. It buys once, on the first day, and never
acts again. So a monthly deposit into the default strategy — which is what the
Backtest tab generates unless a library script is picked — **accumulates in
cash forever.** The feature would ship looking broken to the people most likely
to use it.

This is a decision, not a detail. Options:

1. **Teach `BuyAndHold` to invest new cash.** On a day with a flow, buy at the
   configured weights with the new money only. Small, targeted, and it makes
   buy-and-hold mean "hold, and keep buying", which is what a contributing
   investor means by it. **Recommended.**
2. **A `ReinvestCashflows` config flag** doing the same thing, defaulted off.
   Safer for existing configs, but the default is the broken-looking one.
3. **Leave it to the strategy.** Honest and useless: the shipped Lua library
   would all need updating, and the default still does nothing.

(1) changes no existing result — an existing config has no cashflows, so the
new branch never fires — which is exactly the "default to a zero value that
reproduces the previous behaviour" rule.

### Hazard 5 — a withdrawal that cannot be funded

`Withdraw` just subtracts from `BuyingPower`; it can go negative. A scheduled
withdrawal is **discretionary**, unlike a margin call (which `CLAUDE.md` says
may overdraw precisely because it is not). So it needs a stated policy:

- sell holdings pro-rata to fund the shortfall, or
- withdraw only what cash allows and record the shortfall.

Selling is the realistic one for a retirement backtest — the whole point is
drawing down the portfolio. Whatever is chosen, count it: a run whose
withdrawals could not be met is a **failed** retirement plan, and that is the
headline result, not a footnote. Consider `Metrics.WithdrawalsMissed` and a
diagnostic.

### Config schema

Match the existing sub-table style (`[portfolio.Costs]`, `[portfolio.Margin]`):

```toml
[portfolio.Cashflow]
Amount    = 500.0        # signed: negative withdraws
Frequency = "monthly"    # monthly | quarterly | annually
Start     = "2016-01-01" # optional; defaults to StartDate
```

An absent block means no flows and byte-identical results. A list of schedules
(`[[portfolio.Cashflow]]`) is the obvious extension; one is enough for v1.

Percentage-of-balance withdrawals ("4% a year") are the other half of the
retirement question and want their own field rather than being smuggled into
`Amount`.

**Frequency and the trading calendar:** "monthly" has to mean the first
trading day on or after the nominal date. The engine only has the days in the

## Strategy discovery — T54–T59 · **current priority**

Added 2026-08-17. The delisted-data programme below is **paused at the user's
request**; T39, T51 and T52 stay `todo` but sit behind everything here.

The question these answer: *how does a user get from "I wonder if X works" to a
number they can trust?* Today that path is: hand-write a Lua script, hand-edit

deflated-Sharpe machinery (T15–T19) already makes the *testing* half rigorous.
The **finding** half is untouched, and it is where the leverage is.

What is actually missing, in order of how much it multiplies what a user can try
per hour:

2. **The Lua library is two indicators wide** (`sma`, `rsi`). Every new idea

## T61 — A diagnostics console: show the user what went wrong, and nothing else

**Category:** feature · **Status:** done — `src/backtest/diagnostics.go`,
`ui/frontend/src/ConsolePanel.tsx`. Nine call sites routed; the `data` package
deferred as scoped

Agreed with the user 2026-08-18, after T9 and T13 both stalled on the same
question: they exist to produce a message, and there is nowhere for a message
to land.

**The UI never touches the `log` package at all.** `log.SetOutput` happens only
in `src/main.go:103`, behind the CLI's `-debug` flag. So in the Wails app every
diagnostic the engine emits — a broken Lua script, a truncated run, a
walk-forward window that could not be scored — goes to the stderr of a windowed
desktop application and is seen by nobody. There is currently no path from the
engine to the user for anything that is not a metric.

### The shape, and why it is not "capture the log"

Capturing `log` output and filtering it in the UI was considered and rejected:
the ~65 log sites in `src/` do not separate by any pattern a regex could catch.
They separate by *intent*, which only the call site knows. The engine must
declare what is user-facing.

The codebase already has the idiom: `TransactionLogger` (`portfolio.go:13`) is
a package-level sink defaulting to `io.Discard` that the CLI swaps out under
`-debug`. Mirror it exactly.

```go
// Diagnostic is one thing that went wrong in a way the user can act on.
type Diagnostic struct {
	Level     string // "warn" | "error"
	Portfolio string // "" when not attributable to one portfolio
	Message   string
}

// Diagnostics receives user-facing diagnostics. Nil by default, so the CLI
// and every existing test behave exactly as they do today.
var Diagnostics func(Diagnostic)

// diagf records a user-facing diagnostic and also writes it to the log, so
// `-debug` users lose nothing.
func diagf(level, portfolio, format string, args ...any)
```

The sink is called from the worker pool, so **the installed callback owns its
own locking** — the engine does not lock. The UI installs one collector for
the duration of a run and restores it after, under a package-level mutex,
because the sink is process-global and two concurrent `RunBacktest` calls
would otherwise cross-contaminate.

### Which call sites convert

User-facing — these become `diagf`, keeping their current wording:

| site | what it tells the user |
|---|---|
| `runner.go:287` | how many days actually simulated, and why the rest were dropped |
| `strategy_lua.go:99` | their Lua script failed to initialise (`error`) |
| `strategy_lua.go:106` | their Lua script raised on a given day (`error`) |
| `walkforward.go:268` | no candidate produced a scorable run; window skipped |
| `walkforward.go:281` | the winner produced no test days |
| `metrics.go:267,275,295,598` | the "too few observations to score" family |

Everything else keeps calling `log` and stays invisible to the UI. Explicitly
**not** converted, because it is noise or internal:

- `portfolio.go:168–187` (`PrintMetrics`) — a full dump duplicating the
  results table.
- `database.go:241,284,326` — `Query time: …` telemetry.
- the `scanning X: %v` row-scan warnings across `data/*.go`.
- `runner.go:512,530` — clone/result-write failures. Internal, and if they
  fire the user has a bigger problem than a console message.

### Out of scope — keep it small

- **The `data` package gets no sink.** Its user-relevant messages
  (`fundamentals.go:244,251,259` — falling back to a 90-day lag) are real, but
  `backtest` imports `data`, so `data` would need its own second sink. Nothing
  calls `PointInTimeFundamentals` from a strategy yet (**T33**, `needs-user`),
  so those messages cannot fire in a UI run today. Add it when T33 makes it
  reachable.
- **No streaming.** Collect during the run, return with the results. Live
  output needs `wruntime.EventsEmit`, a frontend subscription and line
  batching; only worth it if the wait turns out to bother the user.
- **`src/main.go` is not touched.** `-debug` keeps writing `backtester.log`
  exactly as it does now. The console is purely additive.
- **No new logging.** Convert existing sites only; do not go hunting for
  things that *should* be reported. T9 and T13 add their own when they land.

### Steps

1. `Diagnostic`, `Diagnostics`, `diagf` in `src/backtest/` (new
   `diagnostics.go`, matching `blotter.go`'s size and comment density).
2. Convert the nine call sites in the table above. Wording unchanged — several

3. `RunBacktest` (`ui/app.go:89`) installs a collector, restores it on exit

4. A console panel in the frontend, modelled on `QueryConsole.tsx`. Errors and

## T63 — `[Output]` field surface: a filter on `Trials` breaks the output file

**Category:** bug · **Status:** done — `src/backtest/reporter.go`

Found 2026-08-18 while looking for simple features, by reading `reporter.go`

Four tests hold the surface together: the two lists agree in both directions,
every numeric field resolves as `float64`, every advertised field is actually

## T65 — Filter a sweep by "beat the baseline" and "better than chance"

**Category:** feature · **Status:** done — `src/backtest/reporter.go`

Added 2026-08-18, the follow-up T64 recorded. `Result.Baseline` and
`Result.Significance` were the last two decision-changing structs `[Output]`
could not reach, which meant the two questions most worth filtering a sweep on
— did it beat equal-weight buy-and-hold, and is it distinguishable from random
timing — could only be answered by reading every row by hand.

Baseline names are **prefixed** (`BaselineSharpe`, `BaselineFinalValue`, …)
because `BaselineStats` carries its own `FinalValue`, `SharpeRatio`,
`MaxDrawdown` and `StandardDev`; an unprefixed name would have resolved to the
wrong one of the two and been almost impossible to notice in a results file.

### The part worth remembering

`BeatBaseline`, `BaselineComputed` and `SignificanceComputed` are **bools** —
the first bool fields in this surface. `evalBinary` already handled them
(equality on any type, and `&&` requires bool operands), so `filter =
"BeatBaseline && Trades > 0"` works with no evaluator change.

The `Computed` flags are addressable because without them the figures they
guard **lie by omission**:

```toml
filter = "PValue < 0.05"                          # WRONG
filter = "SignificanceComputed && PValue < 0.05"  # right
```

An uncomputed `Significance` has `PValue` **0**, which passes `PValue < 0.05`
and reads as maximally significant when nothing was tested. `Baseline` is the
same shape: uncomputed means `Beat` false and the excess figures 0, which reads
as "tied with buy-and-hold" rather than "there was no baseline".
`TestUncomputedSignificanceLooksSignificant` pins this in place and will fail
loudly if a future change ever makes the naive filter safe, so the docs cannot
drift away from the behaviour.

`Draws`, `Seed` and `Significance.Sharpe` are deliberately not addressable:
the first two are reproducibility metadata and the third duplicates
`SharpeRatio`.

## T66 — A reversed `StartDate`/`EndDate` crashes the run

## T67 — A repeated ticker panics, and hides a doubled equity curve

**Category:** bug · **Status:** done — `src/backtest/portfolio.go`

Found 2026-08-18 continuing the invalid-input sweep that produced T66.

`Tickers = ["AAPL", "AAPL"]` — a copy-paste slip in a long list — panics with
`index out of range` at `runner.go:323`. The cause is in `alignToWindow`: it
keys its output map by ticker but appends **once per index**, so a duplicate
appends the same bar twice per day and returns a series of `2n` bars alongside
a reported length of `n`. The day loop then indexes past the end.

The panic was the lucky part. `GetPortfolioValue` also iterates `p.Tickers`
and looks each one up in `p.Positions`, so the single position would have been
counted **twice** — an equity curve inflated by the duplicated holding, with
every metric derived from it wrong and nothing to indicate it.

Rejected at construction rather than deduplicated: weighting a holding up is
what `[portfolio.Params.weights]` and `buy_and_hold_weighted.lua` are for, and
silently dropping a line from someone's config is its own kind of surprise.

`TestAlignToWindowEmitsOneBarPerDay` pins the underlying invariant directly —
one bar per ticker per day, whatever the ticker list says — so a caller that
reaches `alignToWindow` without going through the constructor cannot
reintroduce it quietly.

## T70 — `num_days()`: a strategy could not know its own horizon

**Category:** feature · **Status:** done — `src/backtest/strategy_lua.go`

Added 2026-08-18, continuing through the Lua API after T69.

`step(day)` is handed a 0-based day index and nothing to compare it against, so
a script could not tell where it was in the run. "Do this once, at the end" —
close the book, take a final reading, stop entering in the last month — was not
expressible at all. `num_days()` closes that: every ticker has the same bar
count once the window is aligned (`alignToWindow`, pinned by T67), so one
series answers it.

The last day is `num_days() - 1`, and that off-by-one is the obvious way to get
this wrong, so a test asserts the idiom fires **exactly once, on the final
day** — not never, not twice.

### Why closing out is worth documenting

Realised P&L, win rate and profit factor all come from **sells**. A buy-and-hold
realises nothing, so those three read zero however well it did — which looks
like a broken blotter rather than an accounting choice. Selling on the final bar
makes them describe something, at the cost of one round of fees that will show
up honestly in `TotalFees`. Both `strategies/README.md` and the assistant prompt
now say so, since "why is my win rate zero" is a question the assistant would
otherwise answer badly.

Only one global was added. `last_day()` was considered and rejected: two globals
for one fact, and the documented idiom is clearer than a second name to learn.

## T71 — A misspelled `Params` key silently runs the defaults

**Category:** bug · **Status:** done — `src/backtest/strategy_lua.go`

Found 2026-08-18 reading the shipped strategies as a strategy author rather
than as code, continuing from T69 and T70.

Every script reads its settings the same way: `params.lookback or 126`. So a
key spelled wrong does not error — it **falls through to the default** and the
run proceeds with settings the user did not choose, reporting numbers that look
entirely normal.

In a sweep it is materially worse. `ToPortfolios` merges sweep values into
`Params`, so a mistyped swept key expands to N portfolios differing only in a
value nothing reads. **Every trial produces identical numbers**, while `Trials`
is N and the deflated Sharpe dutifully discounts the result for a search that
never happened — a correction applied to a search of one, presented as a search
of N. The symptom, a sweep where every row matches, does not look like a
spelling mistake, so the diagnostic names the consequence explicitly when
`Trials > 1`.

### Why a source scan rather than instrumenting the table

The obvious implementation — make `params` a recording proxy — does not work
safely here. `__index` fires only on *missing* keys, so recording reads means
handing the script an empty table backed by a metatable, and gopher-lua is Lua
5.1 with **no `__pairs`**. Any script iterating its own params would silently
see nothing. Trading a silent wrong-settings bug for a silent empty-table bug
is not a fix.

Scanning the source cannot break a working script. It can miss a key composed
at runtime (`params[name]`), which is why this warns rather than rejects.

`TestShippedStrategiesReadEveryDocumentedParam` checks the whole shipped
library is clean under the rule, so the warning does not become noise on a
user's first run.

## T72 — `Params` on a built-in strategy are silently discarded

**Category:** bug · **Status:** done — `src/backtest/strategy.go`, `config.go`

Found 2026-08-18 immediately after T71, as its blind spot.

`NewStrategy` passes `params` to the `lua` case **and to nothing else**. So a
`[portfolio.Params]` block on `buyAndHold`, `greedy`, `equalWeights` or
`smaCross` is discarded without a word. T71's per-key check cannot see this: it
lives in the Lua host, and here there is no interpreter to ask.

The severe form is the same as T71's. Sweeping a built-in expands to N
portfolios that are **byte-identical runs**, while `Trials` is N and the
deflated Sharpe discounts the result for a search that never happened.

`smaCross` deserves its own mention and gets one in the message: it is the
built-in people most want to sweep, and its periods live in the **spec string**
rather than in `Params`, so `[portfolio.Sweep] short = [5, 10, 20]` looks
exactly like it should work. It cannot be swept that way at all — one
`[[portfolio]]` block per setting is the only route.

### The bug my own test caught

The first cut checked `pc.Params` only. A swept block usually has **no
`[portfolio.Params]` at all** — the keys arrive in `[portfolio.Sweep]` and are
merged in per combination afterwards — so the check missed precisely the case
that matters most. It now takes the union of both maps.
`TestSweepingABuiltinSaysTheTrialsAreIdentical` failed on the first run and is
the reason this is right.

Warned once per config block, before expansion, so a 200-trial sweep produces
one message rather than 200.

## T74 — Calmar ratio

**Category:** feature · **Status:** done — `src/backtest/metrics.go`

Added 2026-08-18. A deliberate break from the run of bug-hunting: an actual
feature, and the standard drawdown-relative ratio the app was missing.

`CalmarRatio = AnnualReturn / MaxDrawdown`. Both were already computed and both
are percentages, so the ratio is dimensionless and needs no new data or new
pass over the curve.

It answers a question Sharpe cannot. Sharpe penalises volatility in **both**
directions, so a strategy with violent upside is marked down for it. Calmar
counts only the deepest hole the account was ever in — which is the figure that
actually decides whether a strategy gets abandoned partway through, regardless
of what its Sharpe says.

**A portfolio that never declined reports 0, not `+Inf`.** An unbounded ratio
is undefined rather than excellent, and emitting infinity would sort a strategy
that never traded above every real one — the same trap `Trades > 0` exists to
catch (T64). This follows the house convention already set by
`TradeStats.ProfitFactor`, which reports 0 rather than infinity for a run with
no losing trades. The consequence is documented: a Calmar of 0 means either no
drawdown or no return, and `MaxDrawdown` says which.

Landed in the results table, `[Output]` `fields`/`filter`/`sort_by`, `README.md`
and `appReference` — the last of those enforced, since
`TestSystemPromptDocumentsEveryMetric` failed the build until it was written.

## T75 — How long you were underwater, not just how deep

**Category:** feature · **Status:** done — `src/backtest/metrics.go`,
`analytics.go`

Added 2026-08-18, pairing with T74's Calmar.

`MaxDrawdown` says how **deep** the worst hole was and nothing said how
**long**. Those are different failure modes: a 40% drawdown recovered in a
month and a 15% drawdown that took three years are not remotely the same
experience to live through, and only the second gets a strategy abandoned.
`Metrics.LongestUnderwaterDays` is the most calendar days the curve ever spent
below a prior peak, measured peak-to-recovery — and to the end of the run for a
decline never recovered, since "still underwater at the end" is a duration
rather than an absence of one.

### The trap this had to avoid

`Result.Drawdowns` carries only the **top-N by depth** (`topDrawdowns` at
`runner.go:512`). Deriving the metric from that list would have been the
obvious implementation and **silently wrong**: the longest drawdown is
frequently not the deepest, so a shallow decline that dragged on would simply
be missing from the input. `LongestUnderwater` therefore takes every drawdown,
and its doc comment says so.

`TestLongestUnderwaterNeedsEveryDrawdown` builds a curve with a deep fast
decline and a shallow slow one, computes the figure from the full list and from
a truncated one, and asserts they differ — so the test fails if anyone later
"optimises" it to reuse the Result's list.

The count is exposed to `[Output]` as a `float64` per T63; the guard test
would have caught an `int`.

## T76 — `-check`: validate a config without running it

**Category:** feature · **Status:** done — `src/backtest/check.go`, `-check`

Added 2026-08-18. Structurally different from the last two, and it is what
makes this session's other work pay off.

Everything T66–T75 added — reversed windows, duplicate tickers, negative
capital, `Params` reaching a strategy that cannot read them, swept keys nothing
reads, an unusable `[Output]` block — fires while a run is being set up. That
is the right place for it, but it means the only way to learn a config is wrong
is to start a backtest and wait.

`CheckConfig` runs the same construction path and stops there. **It opens no
database and simulates no days**, so a whole config is validated in
milliseconds against a 2.9 GB file it never touches. It reports through the
same `Diagnostics` sink a run uses, deliberately: the point is that `-check`
tells you exactly what the run would have told you, only sooner.

It follows the same fork a run does, including the walk-forward path that
bypasses `ToPortfolios` — the fork that made T73 a bug. A test pins that.

### Two things it catches that a run catches late or not at all

- **`[Output]`.** The results file is opened *after* the simulation, so a typo
  in `fields` is otherwise discovered at the end of a run that is now wasted.
- **Duplicate portfolio names.** Not rejected by the engine, and not a defect
  in any single run — but every result row, log line and research-log entry is
  keyed by that name, so two portfolios sharing one cannot be told apart
  afterwards. A warning, not an error.

Errors exit `1`; warnings alone exit `0`, because a config with warnings still
runs — it just may not do what was meant.

`LoadConfigText` was added alongside, so a config can be checked from a string
rather than only a file. `RunFromConfigText` still decodes its own text and was
deliberately left alone rather than refactored.

## T54 — Screen signals before backtesting them

**Category:** feature · **Status:** done — `src/backtest/signalscan.go`,
`-scan-signals` on the CLI. Measured on 30 large caps 2016–2026: 12-month
momentum IC +0.034 (t +2.34), low volatility negative. **T55 is next** — the Lua
signal library, which turns a screened signal into a strategy in minutes.

A backtest is an expensive way to learn that a signal has no information in it.
The standard funnel is cheap first: measure whether the signal predicts forward
returns at all, across the universe, then build a strategy only around the ones
that do.

### What to build

A signal scanner in `src/backtest`: for a library of built-in signals and a set
of horizons, report per (signal, horizon) how well the signal ranks tomorrow's
winners.

- **Signals** are pure functions of one ticker's bars up to and including day
  `i` — never past it. Start with a dozen that cover the obvious axes:
  trailing return over 21/63/126/252 days, 12-1 momentum (252 skipping 21),
  realised volatility (21d, as a negative signal), 5-day mean reversion,
  distance from the 52-week high, the 50/200 SMA ratio, and a volume trend.
- **The measurement is the cross-sectional rank correlation** (Spearman) between
  the signal on day *t* and the return from *t* to *t+h*, computed per day and
  then summarised: mean IC, its standard error, a t-statistic, the share of days
  with positive IC, and the top-minus-bottom quintile forward-return spread.
- **Sample non-overlapping days** — every `h`th day, not every day. Overlapping
  forward windows make the IC series autocorrelated and inflate the t-statistic,
  which is the single easiest way to make a worthless signal look significant.
  Say so in the output.
- **Refuse to report a cross-section that is too small.** Ranking three tickers
  is not a cross-section; require a minimum (start at 5 usable tickers on the
  day, and skip the quintile spread below 10).

### Constraints

- Pure functions, no database: the scanner takes the same
  `map[string][]data.AssetData` the runner already prefetches, so it costs one
  query and no new data access.
- **No look-ahead, and prove it.** A signal must never see an index past the day
  being scored. Write a test whose signal records the highest index it was
  handed and assert it never exceeds `t`.
- Do not touch the metric formulas in `metrics.go`; IC is a new statistic in a
  new file.

### Tests, all derivable by construction

- A signal that *is* the forward return scores IC = 1.0; its negation, −1.0.
- A constant signal produces no IC rather than a NaN, and no t-statistic.
- A seeded random signal produces |mean IC| near zero and |t| below 2.
- Spearman itself, on hand-computed vectors including a tie.
- The look-ahead guard above.
- Non-overlapping sampling: a 21-day horizon over 100 days yields ~4 samples,
  not 79.

### Definition of done

All four gates. It needs a user-facing way to run it — a `-scan-signals` flag on
the CLI is enough, reading the tickers and window from the existing config — and
`appReference` must learn it, because "which signals are worth trying on my
universe" is exactly what a user will ask the assistant.

## T56 — Event studies: what happens after X?

**Category:** feature · **Status:** done — `src/backtest/eventstudy.go`, `-event-study` on the CLI. Six price-based events, abnormal returns net of the universe. **Earnings and macro events are not included**: they need a DB read in the run path plus the publication-lag rules, and are worth their own task

- Report the event count prominently. Twelve occurrences is an anecdote, and the

## T57 — Is this one result better than chance?

**Category:** feature · **Status:** done — `src/backtest/significance.go`. Random-timing null + block bootstrap, always computed, seeded. The random-ENTRY null from the original spec is not separately implemented: shuffling exposure already produces random entries with the same exposure profile, so a second null would ask the same question

T17 deflates the best of N trials. It says nothing about a single strategy run
once: a Sharpe of 1.4 over ten years might be skill, or might be what a coin
flip looks like on this price path. Users will ask exactly that question.

### What to build

Two null models, both reusing the existing run machinery:

1. **Signal permutation** — shuffle the strategy's *decisions* in time (or its
   signal series) many times, re-score, and report where the real Sharpe falls
   in that distribution as a percentile. This holds the price path fixed and
   destroys only the timing skill, which is the cleanest null for a timing
   strategy.
2. **Random-entry matching** — replace the entries with random ones of the same
   count and average holding period. This is the honest comparison for a
   strategy that is mostly "be in the market sometimes".

Report a percentile and a p-value, not a verdict, and state the number of draws.
Both are embarrassingly parallel and the worker pool already exists — but do not
touch `runner.go`'s choreography; drive it from above.

### Constraints

- Seeded and deterministic: an unreproducible p-value is worse than none.
- Report the cost up front like the sweep cap does; 1,000 permutations of a
  ten-year run is 1,000 backtests.

## T39 — One symbol, two companies: split the 269 recycled series

**Category:** data · **Status:** done 2026-08-20 — `split_recycled.py` +
generation symbols in `src/data/delistings.go`. **`--apply` was run 2026-08-20
on the user's authorisation: 48 symbols split, 91,993 bars moved.**
Headline: it is **120 symbols, not 269** — 149 of the 269 have price series that
BEGIN after the delisting date and were never spliced. Of the 120, 48 are

**Category (orig):** data · **needs T37's `delistings` table loaded**

T37 found and classified them; nothing has split them. A backtest that holds
`DD` from 2015 to 2026 holds DowDuPont until 2019-05-31 and then, with no gap,
break or marker, holds DuPont de Nemours — a different company with different
economics. `SUNE` runs to 2026 although SunEdison went bankrupt in 2016. `COR`
splices CoreSite Realty onto Cencora. This is worse than survivorship bias:
survivorship makes results optimistic, this makes them arbitrary. Confirmed
against the vendor on 2026-08-17 (see `analysis/free_data_sources.md` §3), so
it is Yahoo's behaviour, not a loader bug.

### What to build

1. **A splitting convention.** The default proposed here, unless the user says
   otherwise: keep the live company at the bare symbol and give the dead
   occupant a generation suffix — `DD` stays DuPont de Nemours (2019-06-03→),
   and the DowDuPont era becomes **`DD.1`** (…→2019-05-31), numbering from the
   oldest. Rationale: every existing config that names `DD` keeps meaning the
   company it means today, so nothing silently changes identity, and the
   historical company becomes addressable rather than deleted.
2. **`split_recycled.py`** — read `delistings` ⨝ `stock_data_optimized`, take
   the `recycled` bucket from `ClassifyCoverage`, and rewrite each affected
   symbol's bars into two symbols at the delisting date. Ships `--dry-run`
   (default) printing the exact per-symbol before/after row counts and date
   spans; the real run is the user's.
3. **The join is the hard part, not the split.** A delisting date alone does not
   prove the later bars are a different company — a symbol can be delisted from
   one exchange and relisted on another *as the same company*. Corroborate with
   SEC `formerNames` and CIK (§4 of the sources doc) before splitting, and put
   every symbol that cannot be corroborated in a **`review`** bucket that the
   script prints and does **not** touch. Under-splitting is recoverable;
   wrongly splitting a continuous company is not.
4. **Go side:** `src/data/delistings.go` learns to resolve a generation suffix,
   and `ClassifyCoverage` returns `clean` for a properly split pair — the audit
   that found the defect becomes the test that it is fixed.

### Tests

- `ClassifyCoverage` on a split pair returns `clean` for both halves; on the
  unsplit series it still returns `recycled` (the regression guard).
- Suffix resolution round-trips: `DD.1` parses to (`DD`, generation 1), a bare
  symbol to generation 0, and a symbol containing a dot that is *not* a

### Uncertain — the user should weigh in

- **The suffix character.** `.` collides with the class-share convention

  data alone. Cheaper and safer; loses 269 tickers of history. Splitting is
  proposed because the history is real and it is only the *identity* that was
  wrong.

## T41 — Know what is wrong with each series: a data-quality audit

**Category:** investigation · **Status:** done — `analysis/data_quality.md`,
`add_data_quality.py`, `src/data/data_quality.go`. **The loader is yours to
run**, and acting on the verdicts is **T50** (`needs-user`), below

"Best possible data set" is unmeasurable without a defect inventory. T18 audited
survivorship and T37 audited symbol recycling; nothing has audited the bars
themselves. Read-only, self-contained, and the input to every decision below.

### What to measure, per ticker

- **Gaps** — trading days missing against the NYSE calendar the `$` series
  already use; longest gap and total missing days.
- **Stale runs** — identical closes for N consecutive days (a dead feed looks
  exactly like a flat stock, and one of them ruins a backtest).
- **Zero or missing volume** runs, and bars with `volume = 0` but a price move.
- **Unexplained jumps** — |return| > 50% in one day, minus the ones a split or
  dividend explains, since an unadjusted split is the classic silent killer.
- **Impossible bars** — `high < low`, `close` outside `[low, high]`,
  non-positive prices.
- **Duplicate rows** for a (ticker, date) — the `financials` table had exactly
  this defect (T29), so do not assume the price table does not.
- **Tail staleness** — last bar well before the table maximum, cross-referenced
  against `delistings` so a real death is not reported as a defect.

### Output

1. `analysis/data_quality.md` — the method, the exact SQL, the distribution of
   each defect, and the twenty worst tickers per category.
2. A **verdict per ticker** (`good` / `usable` / `suspect` / `unusable`) with
   the reasons, written by a loader as a `data_quality` table so the engine can
   later refuse to trade an unusable series. Same rules as always: the agent
   ships the loader with `--dry-run` verified, the user runs it.

### Constraints

Read-only SELECTs against a 2.9 GB single-writer file the user may have open.
Sample where a full-table scan would be pathological, and **say in the document
that it was a sample**, with the sampling rule.

## T42 — Why did it delist? Acquisition and bankruptcy are opposite outcomes

**Category:** data · **Status:** done — `add_delisting_reasons.py`,
`src/data/delisting_reasons.go`; all four spot checks pass. **The loader is

## T43 — Point-in-time S&P 500 membership, from free dated tables

**Category:** data · **Status:** done — `add_index_membership.py`,

The larger half of survivorship bias is *selection*, not missing prices: the

## T45 — A series that ends mid-backtest must be an ordinary series

**Category:** feature · **Status:** done — the diagnosis, the tests and the
report shipped; **the semantics change moves existing numbers and is now T49
(`needs-user`)**, directly below

This is the direct answer to *"delisted stocks should be treated the same as
normal stocks in terms of backtesting"*, and it is the one task in this
programme that needs no new data at all. Today the engine has never had to hold
a name that stops existing, because the universe contains no such name (T18).
The moment T39, T43 or any delisted data lands, it will — and nothing has been
tested against it.

### What to establish, by writing the tests first

Take a portfolio holding two tickers on a synthetic path where one ticker's bars
simply stop halfway through the window, and answer each of these with a test:

1. **Valuation.** Does `GetPortfolioValue` carry the dead name at its last price
   forever, drop it, or produce a hole? Whatever it does today, it does silently.
2. **The trading-day intersection.** `runner.go` intersects trading days across
   tickers. If that is an intersection rather than a union, **one delisted name
   truncates the entire backtest window for every other holding** — the most
   likely serious defect here, and cheap to prove either way.
3. **Metrics.** A daily return series with a hole in it feeds Sharpe, Sortino,
   stdev and max drawdown. NaN propagation through any of those is silent.
4. **Correlation.** `correlation.go` pairing a full series against a truncated
   one — mismatched lengths are a panic or a wrong answer, never a right one.
5. **Allocation.** `buyAndHold:equalWeights` sizing across a universe where a
   member has no bars on day 0, and rebalancing into a name that no longer
   trades.

### Then make each one correct

The intended semantics, which need writing down in `README.md` because there is
currently no statement of them anywhere:

- A holding whose data ends is **liquidated at its last available price** on the
  first day it is missing, and the proceeds sit in cash. That is the neutral
  convention; the *return* applied at liquidation is T38's job and defaults to
  0.0, reproducing this exactly.
- The backtest window is **not** shortened by a member's death, and a name with
  no data at the start is simply not held yet.
- Metrics are computed over the portfolio's own continuous equity curve, which
  stays continuous through a member's death.

### Constraints

- `runner.go`'s worker pool and channel choreography are on the `CLAUDE.md`
  denylist. If the fix requires touching the trading-day intersection *logic*,
  that is fine; if it requires touching the *concurrency*, stop and file it.
- No existing number may move. A universe with no delisted names — i.e. every
  config that exists today — must produce byte-identical results, and that is
  the first test to write.
- `go test ./src/backtest/ -race -count=1` is mandatory here.

### Why this is the highest-value task in the programme

Every other task buys data. This one is the difference between that data being
usable and it silently corrupting every result that touches it. It is also the
only one that can be completed today, with no key, no loader and no user action.

## T13 — Any non-zero `slippage_bps` stops buy-and-hold from trading at all

**Category:** bug · **Status:** done — option 1, `generalBuy` sizes against
`Costs.BuyFill(price)`. Backtests that set `slippage_bps` now trade and pay it
instead of sitting in cash, so their numbers change (downward). Nothing without
`slippage_bps` moves

Found by the new end-to-end correctness tests (`correctness_test.go`). Set
`slippage_bps` to anything above zero — **1 basis point is enough** — and the
built-in `buyAndHold` strategies buy nothing for the entire backtest. The
portfolio sits in 100% cash and reports a flat equity curve, with no error
logged anywhere.

Measured, single ticker at a flat price of 100, `BuyingPower = 10000`:

```
slippage    0.0 bps -> shares=100.000000 cash=0.00      traded=10000.00
slippage    1.0 bps -> shares=0.000000   cash=10000.00  traded=0.00
slippage   10.0 bps -> shares=0.000000   cash=10000.00  traded=0.00
slippage  100.0 bps -> shares=0.000000   cash=10000.00  traded=0.00
commission 10.0     -> shares=99.900000  cash=0.00        (clamp works)
```

### Why

`generalBuy` sizes the order against the **quoted** price — `10000/100 = 100`
shares — but `Portfolio.Buy` computes `notional` from the **slipped** fill
price, `100 * 101 = 10100`. That trips the affordability gate at
`portfolio.go:169`:

```go
if notional > p.BuyingPower*(1.0+1e-9) {
    return
}
```

and the order is dropped. Commission takes the clamp branch just below and
fills correctly at a reduced size; slippage never reaches it, because it
inflates the notional itself rather than the total. So the two cost knobs
behave completely differently, and only one of them works.

This contradicts the intent written directly above that gate, which says
rejecting such orders

> would silently stop every spend-it-all strategy from trading the moment
> costs were switched on, which would read as "costs killed the returns"
> rather than as an error.

That is exactly what happens today. `README.md:148` documents `slippage_bps`
as an ordinary knob with no such warning.

### Why the existing tests miss it

`TestSlippageDirection` only checks `BuyFill`/`SellFill` arithmetic in
isolation — that part is correct. `TestCostsAreAlwaysADrag` and
`TestCostsDragScalesWithTurnover` run real strategies but only assert that
costs *reduce* the final value, which stays true when the mechanism is "no
trades happened": a portfolio that never buys underperforms one that does.
A directional assertion cannot distinguish a cost from a silent no-op.

### The test that exposes it

Removed from the committed `correctness_test.go`, which now points here:

```go
func TestSlippageBuysFewerShares(t *testing.T) {
	p := runExact(t, "buyAndHold:equalWeights", exactCash,
		[]string{"AAA"}, map[string][]float64{"AAA": {100, 100}},
		CostConfig{SlippageBps: 100.0})

	almost(t, "fill price", p.Positions["AAA"].AveragePrice, 101.0)
	almost(t, "shares", p.Positions["AAA"].Amount, exactCash/101.0)
	// Marked back to the quoted 100: slippage is a real, immediate loss.
	almost(t, "final value", finalValue(t, p), exactCash*100.0/101.0)
}
```

It currently panics on a nil position, which is itself the symptom.

### Not fixed unattended

Every candidate fix changes the cost model's observable behaviour, so every
existing backtest that sets `slippage_bps` changes its numbers. Your call:

1. **Size against the fill price** — `generalBuy` asks `Costs.BuyFill(price)`
   what a share really costs. Most correct, and makes slippage behave like
   commission, but the sizing helper has to learn about costs.
2. **Clamp in `Buy`** — extend the existing commission clamp to cover a
   notional overshoot from slippage. Smallest diff, keeps the knowledge in
   one place, but silently resizes orders the caller asked for.
3. **Reject loudly** — keep the current behaviour but log it, so it reads as
   an error rather than as a return. Honest, but leaves the knob unusable.

I'd take (1): it is the only one where `slippage_bps = 1` means "fills are
0.01% worse" rather than "the strategy stops trading".

### Resolution plan — say "T13: do it" and this executes

**Recommended: option 1, size against the fill price.** It is the only option
where the knob does what its name says, and it makes slippage behave like
commission instead of like a kill switch.

1. `generalBuy` takes the `CostConfig` and sizes against `Costs.BuyFill(price)`
   rather than the quoted price. That is the whole fix: the caller then asks
   for a quantity it can actually afford, and `Buy`'s existing gate passes.
2. `buy_max` in `strategy_lua.go` routes through the same path, so Lua
   strategies get the fix for free and the Lua API surface does not change.
3. Restore `TestSlippageBuysFewerShares` to `correctness_test.go` from the

## T15 — Parameter sweeps: one config block, N runs

**Category:** feature · **Status:** done · **do this before T16–T17**

Today one `[[Portfolio]]` block is exactly one parameter set, so "find a
strategy" means hand-editing `config.toml` and re-running. This is the single
biggest gap between the app being a backtester and being a strategy-finder,
and most of the machinery already exists: `runner.Run` takes `[]*Portfolio`
and fans out across `NumCPU` workers, and `[Output]`'s filter/sort/limit is
already the right way to reduce a large result set.

### What to add

A `[portfolio.Sweep]` block whose values are **lists**, expanded into the
cartesian product of portfolios before the runner ever sees them:

```toml
[[Portfolio]]
Name        = "RSI"
BuyingPower = 10000.0
StartDate   = "2015-01-01"
EndDate     = "2025-01-01"
Tickers     = ["AAPL"]
Strategy    = "lua:strategies/rsi.lua"
[portfolio.Params]
  period     = 14        # base values
  buy_thresh = 30
[portfolio.Sweep]
  period     = [7, 14, 21]
  buy_thresh = [20, 30]
```

That is 3 × 2 = 6 portfolios. Each one takes the base `Params` with its own
sweep values written over the top, so a key that is swept overrides its base
value and a key that is not is inherited unchanged.

### Constraints

- **Expand in `config.go`, at `ToPortfolio` time or just above it.** The
  runner must not learn about sweeps: its worker pool and channel choreography
  are on the `CLAUDE.md` denylist, and it does not need to change — N
  portfolios is what it already accepts.
- **This task is the explicit authorisation to extend the TOML schema**, which
  the scope rules otherwise forbid. It extends it only: a config with no
  `[portfolio.Sweep]` block must produce exactly one portfolio with exactly
  today's `Params`, and byte-identical results.
- **Deterministic order.** Iterate sweep keys in sorted order and values in
  their listed order, so the same config always yields the same portfolios in
  the same sequence. A sweep whose result order changes between runs cannot be
  diffed, which defeats the point.
- **Name each run for its parameters**, e.g.
  `RSI [buy_thresh=20 period=7]` — sorted keys, so the label is stable. Six
  rows all called "RSI" is an unreadable results table, and the name is the
  only place the parameter set survives into `[Output]`.
- **Cap the product.** Five keys with ten values each is 100,000 backtests and
  a hung UI. Refuse above a named constant (start at 1000) with an error that
  states the computed count and the cap, rather than starting the run.
- Sweep values must support the same scalar types `Params` already does
  (integer, float, string, bool). A non-list value under `[portfolio.Sweep]`
  is a config error, not a silently-accepted single value.

### Tests

In `config_test.go`, plus an end-to-end case in `correctness_test.go`:

- 3 × 2 sweep yields exactly 6 portfolios, with the exact expected set of
  `Params` maps — assert the whole set, not just the count.
- Sweep values override base `Params`; unswept base keys survive.
- Ordering is deterministic across repeated expansion of the same config.
- Names are unique and encode the parameters.
- **No `[portfolio.Sweep]` block gives one portfolio whose `Params` are `==`

- The cap rejects an oversized product with an error naming the count.
- End to end: a two-value sweep over a strategy on a known price path produces

All four gates in `CLAUDE.md`. `README.md` gets a `[portfolio.Sweep]` section
next to `[portfolio.Costs]`, and `appReference` in `ui/chat.go` must learn the

## T16 — In-sample / out-of-sample split

**Category:** feature · **Status:** done

Sweeps without this are a machine for producing overfitted results: 200
parameter combinations over ten years of AAPL will always yield a Sharpe above
2, and nothing in the app will say it is meaningless. The cheapest honest
defence is to report every run twice — on the window it was chosen with, and
on a window it never saw.

### What to add

```toml
[portfolio.Validation]
  in_sample_end = "2021-01-01"   # split date inside [StartDate, EndDate]
```

With it set, each result carries metrics for the in-sample and out-of-sample
segments alongside the full-window metrics it already has. Absent, nothing
changes.

- Add a nested `SplitMetrics` (or similar) to `Result`, holding the two
  segments' `Metrics` plus their date ranges. **Do not add fields to
  `Metrics`** — same reasoning as `BenchmarkStats` in T14: `Metrics` describes
  one series over one window, and the reporter, `[Output] fields` and the
  results table would otherwise report three subjects per row.
- Compute both segments from the single existing run by slicing its daily
  returns and value series at the split date. Do **not** run the backtest
  twice: a second run from a fresh portfolio would start the out-of-sample
  half with a flat balance and no positions, which is a different experiment
  and would silently misreport every strategy that holds across the boundary.
  Recomputing max drawdown on a slice is correct; recomputing CAGR needs the
  slice's own elapsed years.
- Surface both segments in the results table, and mark the out-of-sample
  column as the one that counts.
- Reject a split date outside the window, or one leaving fewer than ~30
  trading days on either side, with an error naming the dates.

### Tests

- A split at the exact midpoint of a known price path gives two segments whose
  compounded returns multiply back to the full-window return.
- Full-window metrics are unchanged by adding a split — this is the guard that
  the slicing did not disturb the run itself.
- No `[portfolio.Validation]` block leaves the new fields empty and every
  existing number identical.
- An out-of-range or too-narrow split date errors rather than producing a
  one-sided result.

### Definition of done

All four gates. The assistant must learn to *recommend* this, not just accept
it: when a user asks it to sweep parameters, proposing a split is the correct

## T17 — Overfitting statistics: trial count and deflated Sharpe

**Category:** feature · **Status:** done

**Split from the original T17 during implementation.** That task bundled
walk-forward with the overfitting statistics; each is the size of a whole
feature, and the protocol wants one task per commit. Walk-forward is now
**T19**, directly below, and depends on this.

A single split is one draw. This is the rest of the defence, and it is what
separates a strategy-finder from a curve-fitter.

Note the ordering dependency is real, not cosmetic: nothing in this engine is
"fitted" — strategies take parameters, they do not estimate them. So
walk-forward here means *re-selecting the best parameter set on each training
window*, which is meaningless until T15 exists to generate the candidates.

### What to add

1. **Walk-forward.** Roll a train/test window across the history —
   `train_days`, `test_days`, `step_days` — selecting the best parameter set
   on each train segment by a stated objective (Sharpe by default, and say so
   in the config), then scoring it on the untouched test segment. Concatenate
   the test segments into one out-of-sample equity curve and report its
   metrics as the headline. That curve is the honest answer to "what would
   this have done", and it should be plottable next to the naive one.

2. **The trial count.** Record how many parameter sets were evaluated to
   produce a reported result, and carry it on the `Result`. This number is
   already known — it is the size of the sweep — and it is the input every
   overfitting correction needs.

3. **Deflated Sharpe.** Discount the best observed Sharpe by the number of
   trials that produced it. A tool reporting *"best Sharpe 2.1 across 200
   trials, deflated 0.4"* is a fundamentally different product from one
   reporting 2.1. Implement the standard deflated-Sharpe formulation, cite the
   source in a comment, and **add it as a new function in `metrics.go` — do
   not modify any existing metric formula**, which the scope rules forbid.

### Constraints

- Walk-forward multiplies the run count by the number of windows, on top of
  the sweep. Reuse T15's cap logic and report the total up front.
- The selection objective must be explicit in the config and recorded on the
  result. A hidden objective is the thing that makes walk-forward results
  unreproducible.

### Tests

- On a path where one parameter is unambiguously better in every window, the
  walk-forward selection picks it every time.
- The concatenated out-of-sample curve compounds to the product of its
  segments, and contains no training-window days.
- Deflated Sharpe equals the raw Sharpe at one trial, decreases monotonically
  as the trial count rises, and never exceeds the raw figure.
- A strategy with genuinely no edge over random paths produces a deflated
  Sharpe near zero even when the raw best-of-N looks good. This is the test
  that proves the feature does its job; build it from seeded synthetic data so
  it is deterministic.

### Definition of done

All four gates. This one is worth a `README.md` section of its own explaining
*why* the deflated figure is the one to trust — a number users do not
understand is a number they will ignore in favour of the flattering one.

## T18 — Survivorship bias: measure it before trusting any of this

**Category:** investigation · **Status:** done — see `analysis/survivorship.md`.
The answer is that the universe IS survivor-only; follow-up filed as T20.

The default `config.toml` backtests `AAPL, MSFT, GOOGL, AMZN, NVDA` over

## The research loop — T22–T27

These six tasks turn the app from "a thing that measures a strategy you wrote"
into "a thing that proposes strategies and decides whether they are real". They
are ordered by dependency, and the order is load-bearing: building the
generator before the guardrails produces a machine for manufacturing false
positives at scale.

**Read this before starting any of them.** An idea generator running against a
survivor-only universe (T18/T20) will find beautiful edges that do not exist.
Two consequences:

- **Do T20 Tier 0 first**, so every generated result carries the caveat.
- **Aim the generator at `$`-benchmark asset allocation first.** Those series
  are survivorship-free by construction, which makes cross-asset allocation
  the one space in this app where an automated search is currently honest.
  Single-stock strategy search should wait for real delisted data.

The honest summary of the sequence: T22 gives you memory, T23 makes the memory
count against you, T24 and T25 make a single candidate hard to fake, T26 runs
the loop, T27 widens what it can express.

## T22 — Experiment registry: remember every run

**Category:** feature · **Status:** done — `src/backtest/registry.go`, `-record` / `-campaign` / `-history`. Append-only `research.db`, off by default. **The hypotheses table from the spec is not built** — it belongs with T26, which is still `needs-user`, and an empty table nothing writes to would be worse than none

Nothing persists. `output.txt` is truncated each run, so the app has no memory:
you cannot compare today's idea to last week's, cannot tell whether you have
already tested a hypothesis, and — most importantly — cannot count how many

A `research.db` (a **separate** DuckDB file — `stock_data.db` is single-writer

## T23 — Campaign-level deflation: count every trial you ever ran

**Category:** feature · **Status:** done — campaign trial count + bar stored per row and reported at record time. **The UI 'trials spent' readout now exists** as the third verdict card in `ResultsView.tsx` (trials, deflated Sharpe, and the no-edge best-of-N bar). Campaign-level totals are still CLI-only

T17 deflates a result by the trials *in its own sweep*. That is the right
correction for one config block and the wrong one for a research programme: an
agent that tries 40 hypotheses × 50 parameter sets has run 2,000 trials, and
deflating the winner by 50 overstates it enormously.

### What to build

- A campaign id grouping every run made in pursuit of one question.
- `DeflatedSharpe` computed against the **campaign's** cumulative trial count
  and Sharpe spread, read from the registry, alongside the existing per-sweep
  figure. Report both, labelled: the per-sweep number is the optimistic one.
- A "trials spent" readout in the UI, because a budget you cannot see is not a
  budget.

### Why it matters more than it sounds

This is the difference between a research tool and a slot machine. Every
strategy-search product that has ever produced garbage produced it by
deflating against the wrong denominator. Getting this right is most of the
scientific value of the whole loop.

### How you know it worked

- Twenty sequential single-strategy runs in one campaign produce a
  campaign-deflated Sharpe materially below each run's per-sweep figure.
- The campaign figure is monotonically non-increasing as runs are added.
- A synthetic campaign of pure random walks ends with campaign-deflated
  confidence near zero however many are run — the T17 test, extended across
  runs rather than within one sweep.

## T24 — Robustness battery: one number that is hard to fake

**Category:** feature · **Status:** done (2 of 5 checks) — cost and start-date sensitivity, `-robustness`. **Parameter-neighbourhood and universe subsampling are NOT built**: both need sweep awareness, which is different machinery. Block bootstrap already shipped with T57. No aggregate RobustnessScore — with two components it would hide more than it says

A Sharpe from one window with one parameter set and one cost assumption is a
point estimate dressed as a finding. Every candidate worth reporting should
survive being pushed on, automatically.

### What to build

A battery that runs on any result, reusing the sweep machinery:

1. **Cost sensitivity** — re-run at 0 / 5 / 20 / 50 bps round-trip. Report the
   cost level at which the edge reaches zero. "Dies above 7bps" is a complete
   review in three words.
2. **Start-date sensitivity** — shift the window start by ±5, ±20, ±60 trading
   days. A result that only exists for one start date is a calendar artifact.
3. **Parameter neighbourhood** — score the swept winner's immediate neighbours.
   A winner on a plateau is plausible; a winner that is a spike between two bad
   neighbours is overfit, and this is the single most diagnostic check here.
4. **Universe subsampling** — drop a random 20% of tickers, repeat, report the
   spread. (Meaningless for single-ticker runs; skip rather than fake it.)
5. **Block bootstrap** — resample daily returns in ~20-day blocks, 1,000 times,
   for a confidence interval on Sharpe and max drawdown.

Aggregate to a `RobustnessScore` in 0–1, with the components always shown
beside it — a score whose parts are hidden is a number people will learn to
game.

### Constraints

- Every element reuses existing machinery. No new metric formulas.
- It multiplies run count substantially, so it is opt-in per config and must
  report its cost up front, like the sweep cap does.

## T25 — Candidate validation: reject bad strategies before they score

**Category:** feature · **Status:** done — `src/backtest/validate.go`, `-validate <spec>`. All four checks. Note the T13/T9 dependency was **not** blocking: the validator's job is to catch those, and its tests reproduce both

If the assistant is going to write strategies unattended, a generated script
must clear a gate before its numbers mean anything. Right now a strategy that
peeks at future data, or never trades, or quietly loses cash to a typo'd
ticker, produces a perfectly plausible-looking result.

### What to build

An adversarial fixture suite every candidate runs against before it is scored:

1. **Look-ahead detection.** Run the strategy twice on identical history except
   that all bars after day *k* are replaced with noise. Any difference in
   behaviour at or before day *k* proves the strategy read the future. This is
   a genuinely reliable detector and nothing in the app has one.
2. **Degenerate inputs** — flat prices, a single gap, a series that only falls,
   one bar. Must not panic, must not produce NaN.
3. **Did it trade?** Zero trades is not a strategy; report it as invalid rather
   than as a 0% return.
4. **Cash conservation.** Final value must equal start plus mark-to-market plus
   realised P&L minus fees, to the cent. T13 and T9 are both violations of this
   invariant, which is why they are prerequisites — the check would fail today.

### Why it depends on T13 and T9

Both are live cash leaks. A validator asserting conservation cannot ship while
the engine violates it; conversely, once it ships, that entire class of bug
becomes impossible to reintroduce.

## T26 — The loop: hypothesis in, verdict out

**Category:** feature · **Status:** done for the ENGINE — `src/backtest/hypothesis.go`, `-hypothesis <file.toml>`. Pre-registration, mechanical judging, three verdicts, the agreed guardrails (200 trials, 0.90 deflation, OOS baseline, robustness 0.6) and T33's coverage gate. **Nothing can return `survives` yet** and that is deliberate: condition 4 needs T24's unbuilt parameter-neighbourhood check, so it reports unavailable and good results read `inconclusive`. **The UI hypothesis panel is now built** (2026-08-19): a pre-registration box above the run button and a `Hypothesis verdict` panel in the results

The payload. Everything above exists so this can be trusted.

### The cycle

1. **Pre-register.** A hypothesis is recorded *before* it runs: the claim in
   one sentence, the universe, the window, the parameter space, and — the part
   that does the work — **the success criterion, chosen in advance**. Deciding
   what counts as success after seeing results is the mechanism by which
   backtests lie, and writing it down first is the cheapest possible fix.
2. **Synthesize.** The assistant writes or parameterizes a strategy for the
   claim, preferring the shipped library over new Lua.
3. **Validate** (T25). Fail closed.
4. **Run** the sweep, the split, and — if it survives — walk-forward.
5. **Stress** (T24).
6. **Judge** against the pre-registered criterion and the campaign-deflated
   confidence (T23). Three verdicts only: *survives*, *rejected*, *inconclusive*.
   "Inconclusive" must be common; a loop that never says it is not testing
   anything.
7. **Record** (T22) and report — including every rejection. A research log that
   only contains successes is a marketing document.

### Constraints

- **A trial budget per campaign, declared up front**, and the loop stops when
  it is spent rather than searching until something passes.
- Never mutate a hypothesis's success criterion after seeing its result. If the
  question changes, that is a new hypothesis with a new id.
- The assistant proposes; it never marks its own homework. The verdict comes
  from the pre-registered criterion, mechanically.

### Why `needs-user`

This is the design that decides what the product *is*, and the guardrail
choices — budget size, what "survives" means numerically, how much autonomy the
generator gets — are yours. The six tasks above are all useful independently;
this one should not start until you have opinions on it.

### Resolution plan — concrete defaults, so "yes" is a valid answer

You said the guardrails are yours to choose. Here are the numbers I would
choose, with reasoning, so the decision is agreement or amendment rather than
design from scratch.

**Trial budget: 200 per campaign.** Large enough to search a two-parameter
space properly, small enough that the campaign-deflated Sharpe (T23) still has
power — past a few thousand trials the correction dominates everything and no
result can clear it, which is mathematically honest but practically useless.
Declared up front; the loop stops when spent, never "one more sweep".

**"Survives" means all four, not any:**
1. The pre-registered criterion, whatever it said.
2. Campaign-deflated confidence **≥ 0.90**. Not 0.95 — with a few hundred
   trials over a few thousand days, 0.95 is close to unachievable and the loop
   would only ever say "inconclusive". 0.90 is demanding without being a wall.
3. Beats the T32 baseline **out of sample**, net of costs. Most strategies do
   not beat buy-and-hold and this is the cheapest way to find out.
4. Robustness score (T24) **≥ 0.6**, with the parameter-neighbourhood
   component non-zero — a winner that is a spike between two bad neighbours
   fails regardless of its other numbers.

**Autonomy: start at level 1 of 3.**
- *Level 1 — propose only.* The agent writes the hypothesis, the criterion and
  the config; you approve before anything runs. Every result is honestly
  attributable and the trial count cannot run away.
- *Level 2 — run pre-approved classes.* You approve a hypothesis *family*
  ("trend-following on `$`-benchmarks") and the agent runs campaigns inside it.
- *Level 3 — autonomous campaigns.* Only worth it once levels 1 and 2 have
  produced a track record you trust.

Starting at 1 costs almost nothing: the expensive part is the machinery, and
raising the level later is a config change.

**One rule I would not make configurable:** the agent never edits a
hypothesis's success criterion after seeing its result. If the question
changes, it is a new hypothesis with a new id and the old one is recorded as
rejected. Every way this kind of system goes wrong routes through that door.

Say **"T26: agreed"** to take these as written, or name the numbers you want
changed.

## T29 — Point-in-time fundamentals: the lag that makes them usable

**Category:** feature · **Status:** done — shipped with T28; nothing consumes
it yet (no Lua API surface), which is deliberate and noted below

`financials.date` is the **fiscal period end**, not the publication date — the
distribution is overwhelmingly 12-31, 03-31, 06-30 and 09-30. Joining it to
prices on that date is look-ahead bias of the most damaging kind: it trades on
Q4 numbers on December 31, roughly four to eight weeks before anyone knew them.
Any factor backtest built that way will look wonderful and be worthless.

`earnings_calendar` holds actual report timestamps (`AAPL 2026-01-29 16:00`,
after the close) for **1,029 tickers** — every one of which has financials.
That is the correct lag where it exists, and 15% coverage where it does not.

### What to build

A point-in-time view, in `src/data`, that is the *only* sanctioned way to read
fundamentals:

1. **Exact lag where possible.** Join a fiscal period to the first
   `earnings_calendar` timestamp strictly after its period end; that is the
   date the figure becomes knowable. Times are after the close, so the first
   tradeable bar is the *next* session.
2. **Conservative lag otherwise.** For the ~85% with no earnings date, apply a
   fixed lag — 90 calendar days is the usual conservative choice for quarterly
   filings and is late enough to be safe for almost all filers. Make it a
   constant with the reasoning next to it, not a magic number.
3. **Flag which rule applied**, per row. A result built mostly on the fallback
   deserves to be read differently from one built on real report dates.
4. **Never expose the raw table** to the Lua API or the assistant's query path
   without the lag applied. The whole point is that the unsafe join should be
   hard to write by accident.

### Also worth fixing while in there

The raw table has duplicate rows — `AAPL / Ordinary Shares Number /
2025-09-30` appears twice with identical values. Deduplicate in the view and
report the count, since a silent duplicate skews any per-ticker aggregate.

### How you know it worked

- No fundamental value is ever visible on a date before its report timestamp.
  Test it directly: for every ticker with an earnings date, assert the view
  returns nothing for that period on the day before publication.
- A ticker with no earnings date returns its period only after the fixed lag.
- The T25 look-ahead detector, once built, passes on a factor strategy written
  against this view and fails on one written against the raw table. That is
  the strongest possible check and worth building the pair together.

peeks is the same bug as a fundamental that peeks, and harder to notice.

## T33 — Expose fundamentals to Lua strategies

**Category:** feature · **Status:** done — `src/backtest/strategy_lua_fundamentals.go`, `Fundamentals` config key, `fundamental()` / `market_cap()`, `Metrics.FundamentalCoverage`, `Fund Cov %` column. **One deviation:** the plan put a <50%-coverage gate in T25, but `ValidateStrategy` runs on synthetic in-process data with no database, so coverage there is always 0 and the gate would fail every strategy. Moved to T26's verdict criteria, where a real run exists

`src/data.PointInTimeFundamentals` (T29) is correct and tested and **nothing
calls it**. Fundamentals are unreachable from a strategy, so the whole Tier B
hypothesis space in `analysis/hypothesis_space.md` — value, quality, leverage,
size, earnings drift — is still untestable.

Closing that needs a Lua API surface, which is a public contract for
`strategies/*.lua` and so is yours to shape. The shape I would propose:

```lua
-- Latest figure PUBLISHED on or before `day`. nil when nothing is known yet.
fundamental(ticker, "Net Income", day)     --> number or nil
market_cap(ticker, day)                    --> shares x close, or nil
```

Design questions that are genuinely yours:

1. **Should `nil` or `0` be returned when nothing is published yet?** The rest
   of the Lua API returns 0 out of range (`price()` does), and the strategies
   README tells authors to guard with `> 0`. But 0 is a legitimate value for a
   fundamental, so consistency and correctness point opposite ways here.
2. **Prefetch or lazy?** The runner prefetches all price history in one query.
   Fundamentals could ride along, but the metric list would have to be
   declared in the config, since fetching all metrics for all tickers is 8.5M
   rows.
3. **Should the engine refuse a fundamental strategy outside 2020-2026?** The
   data simply is not there before then, and a strategy that silently sees
   `nil` for the first fifteen years of its window will look like it has an
   edge in the back half.

The look-ahead guarantee is already enforced in Go, so whichever shape you
pick cannot leak future data — that part is settled.

### Resolution plan — say "T33: do it" and this executes with these answers

**1. Return `nil`, not `0`.** The `price()` convention exists because a price
of zero is impossible, so 0 safely means "absent". That reasoning does not
transfer: a company can genuinely have zero net income, zero cash, or negative
equity, so 0 would be indistinguishable from "not published yet" — exactly the
ambiguity that produces a strategy trading on a value it never had. `nil`
forces the author to handle the gap. Document the asymmetry explicitly in
`strategies/README.md`, since it breaks an otherwise consistent rule.

**2. Declare metrics in the config; prefetch them.** Lazily querying 8.5M rows
per ticker per day would be unusably slow, and the runner already prefetches
all price history in one query. So:

```toml
[[Portfolio]]
Fundamentals = ["Net Income", "Stockholders Equity", "Ordinary Shares Number"]
```

An empty or absent list fetches nothing and costs nothing, keeping every
existing config identical.

**3. Do not refuse an out-of-range window — measure and report it.** Refusing
is too blunt; a strategy may legitimately act only when fundamentals exist.
But the silent failure is real: a strategy seeing `nil` for fifteen years and
then trading looks like it found an edge in the back half. So add
`FundamentalCoverage` to `Result` — the fraction of simulated days on which
the declared metrics were actually available — surface it in the results table,
and have the T25 validation harness treat coverage below 50% as invalid rather
than as a result. That makes the trap visible without forbidding the case.

### The API

```lua
fundamental(ticker, metric, day)   --> number, or nil if not yet published
market_cap(ticker, day)            --> shares x close, or nil
```

Two functions only. Everything else — ratios, rankings, cross-sectional
sorting — is arithmetic a strategy can do itself, and inventing a wider
surface before anything uses the narrow one is how APIs get bloated.

**Effort:** medium — a config field, a prefetch path, two Lua globals, a
coverage metric, and tests that a strategy cannot see an unpublished figure
(the Go layer already guarantees it; the test proves the Lua binding does not
undo it).

## T38 — Apply a delisting return when a holding dies

**Category:** feature · **Status:** done 2026-08-20 — `src/backtest/delisting.go`,
`DelistingReturn` on `[[portfolio]]`, `DelistedHoldings` /
`UnclassifiedDelistings` metrics. **Built reason-aware**, which the analysis
below argued for: only bankruptcy and compliance removals are haircut,
acquisitions keep their last close, and an unidentified reason is counted rather
than guessed at. Default 0.0 reproduces every previous result exactly.

### Why this stopped being a `todo`

Two of this task's premises are now false, and the right shape depends on both.

**1. "A position that delists mid-backtest quietly evaporates" does not happen.**
`validateCoverage` (`runner.go:373`) REJECTS any portfolio whose window runs
past a ticker's last bar, naming the ticker and its real range. So there are
only two reachable cases, and neither is the one described:
  * *Today, before `split_recycled.py --apply`*: the death is invisible because
    the recycled splice hides it. Holding `SUNE` from 2014 to 2020 validates
    cleanly (verified) and silently swaps SunEdison for SUNation in 2016. That
    is T39's bug, not a delisting-return bug.
  * *After the split*: `SUNE.1` ends 2016-04-21, and the same portfolio is
    REFUSED rather than evaporating. Loud, not quiet.
  So `DelistingReturn` has no obvious trigger point. Deciding where it fires —
  at a holding's final bar, at window end, or by relaxing `validateCoverage` to
  permit a holding that dies inside the window — is a semantics decision, not a
  field name, and it is the actual content of this task.

**2. "The free feed carries no delisting reason" is out of date.** T51 shipped
`src/data.ReasonsByMatchedSymbol`, which resolves 1,893 of 7,454 non-ETF symbols
(25.4%) to acquired / voluntary / compliance / bankruptcy. That changes the
design: a blanket Shumway haircut would penalise the acquisitions, and the
acquisitions are the MAJORITY of what T51 resolves (1,352 of 1,893). A reason-
aware rule — haircut performance-related delistings, leave acquisitions at their
last close, fall back to the configured default for the 75% still unknown — is
strictly better than the fixed haircut proposed below, and is a different
feature.

### What was true and still stands

The literature constants: Shumway & Warther (1999) −55% for Nasdaq, Shumway
(1997) the smaller NYSE/AMEX figure usually applied as −30%. A TOML field
defaulting to 0.0 reproduces today's numbers exactly.

### Original text

With T37's registry in place, a position in a company that delists mid-backtest
still quietly evaporates at its last known price. The convention that makes
that honest is a delisting return: a bankruptcy is roughly −100%, not a missing
row.

The complication is that Alpha Vantage's free feed carries **no delisting
reason**, so an acquisition at a premium and a Chapter 11 are indistinguishable
in the data. The literature's answer is a fixed haircut on performance-related
delistings — Shumway & Warther (1999) establish −55% for Nasdaq, Shumway (1997)
the smaller NYSE/AMEX figure usually applied as −30% — but applying either
without knowing the reason overcorrects every acquisition.

So this needs a TOML config field, which is a schema change and therefore the
user's call on shape. Suggested: `[portfolio] DelistingReturn` defaulting to
**0.0**, reproducing today's numbers exactly, with the Shumway constants
exported as named values the user can opt into.

## T95 — Saving the Lua tab recreates the shadow directory T86 deleted

**Category:** bug · **Status:** done 2026-08-23 — `resolveAppPath` in
`ui/app.go`, shared by `ReadFile` / `FileExists` / `WriteFile`

`ui/gallery_test.go` failed mid-session with "ui/strategies exists again". It
was right, and nothing in the session's diff caused it — **the running app
created it.**

```
App.tsx:65   const DEFAULT_LUA_PATH = "strategies/example.lua";
App.tsx:327  await WriteFile(luaPath, luaText);
app.go:490   func (a *App) WriteFile(path, content string) error   // os.WriteFile, relative to cwd
```

Reads of a `lua:strategies/...` spec go through the engine's **parent-walk**
and land on the root library. The write does not: `os.WriteFile` resolves
against the process's cwd, which is `ui/` under `wails dev`. So saving the Lua
tab creates `ui/strategies/example.lua` — and from that moment it **shadows the
root library** for that filename, which is exactly the bug T86 removed. The
file it left behind this time was **zero bytes**, so the shadowed strategy
would have done nothing at all.

The same applies to `WEIGHTED_LUA_PATH` (`strategies/buy_and_hold_weighted.lua`),
which every custom-allocation buy-and-hold config points at. Shadowing that one
with an empty file silently stops the default form's runs from trading.

### Why it is not fixed in this session

It is a path-resolution change in a method (`App.WriteFile`) that every save
goes through, including the TOML tab, and it surfaced while doing T93/T94.
Mixing it into a feature commit is how a one-line fix becomes unreviewable.

Likely shape: resolve a relative script path through the same parent-walk the
engine uses before writing, rather than letting cwd decide — and add a test
that saves to `strategies/x.lua` from `cwd=ui` and asserts nothing appears at
`ui/strategies/`. Check whether `tomlPath` has the same problem.

### Fixed

The root cause was one step earlier than the write. `FileExists` did not
parent-walk either, so from `cwd=ui` the Lua tab could not see the library at
all: it reported "new file, will be created on Save", left the buffer empty,
and Save then wrote that empty buffer to a fresh `ui/strategies/example.lua`.
That is why the stray file was zero bytes.

`resolveAppPath` now maps a relative path onto the file the engine would read,
walking the same parents as `backtest.resolveLuaPath`. Absolute paths (what the
file dialogs produce) pass through untouched; an existing file wins nearest
first, so cwd still shadows a parent exactly as before; a file that does not
exist yet goes where its parent DIRECTORY exists, so a new
`strategies/mine.lua` lands in the library the gallery lists rather than in a
new directory beside the binary.

Proven in both directions: with the helper present but unused,
`TestDefaultLuaScriptIsVisibleFromUI` fails on exactly the reported symptom
("FileExists is false from cwd=ui"); with it wired in, it passes and the Lua
tab loads the real script.

HOLDINGS/GROUP` suffix set) plus a similarity score, and a `matched_by` column
recording which rule fired.

Constraints that matter more than the matching:

- **The delisting dates must agree.** Two companies can share a name; the same
  company delisting on the same date is far stronger evidence than the name
  alone. Require the dates within ~30 days and record the gap.
- **Ambiguity is not a match.** If two EDGAR filers normalise to one registry
  name, record both and mark it `ambiguous` rather than picking one. A wrong
  join here silently attributes a bankruptcy to the wrong symbol, which is worse
  than no join at all.
- **Pure, and tested on the hard cases**, in the shape of the other classifiers
  in `src/data`. The four verified companies from T42 are the obvious fixtures.

Only once this exists does T38 have what it needs: a symbol, a date, and a
reason.

## T53 — Use the real publication date, not period end + 90 days

**Category:** feature · **Status:** done — `src/data/fundamentals.go`. Inert
until `add_sec_financials.py` has been run; the 90-day fallback was deliberately
left at the worst case rather than retuned to the measured median.

T44 measured what the fallback costs. `PointInTimeFundamentals` dates a figure at
the `earnings_calendar` report date where one exists and **period end + 90 days**
otherwise, and `sec_financials.filed` now says what the real answer is:

> median **48 days**, p10 31, p90 62, max 90.

So the fallback is the *worst case*, not a typical one, and every fundamental it
touches arrives about six weeks later than it did in reality. That is
conservative — it cannot manufacture look-ahead bias — but it throws away real
signal, and it is now fixable with measured data rather than a guess.

### What to change

Extend the precedence `fundamentals.go` already implements, in this order:

1. `sec_financials.filed` — the actual filing date, matched on (ticker or CIK,
   metric, period end), taking the **earliest** filing that carried the figure
   (`src/data.FirstKnown` already does exactly this reduction).
2. `earnings_calendar` report date + 1 day — unchanged.
3. Period end + `FixedReportLagDays` (90) — unchanged, and it must stay the
   fallback rather than being retuned to 48. A median is not a floor: using it
   would make roughly half of all figures arrive *before* they were published,
   which is the bias this whole helper exists to prevent.

Each point already records which rule applied; add the new rule to that
vocabulary so a result resting mostly on the fallback stays legible.

### Constraints

- **Absent table, identical numbers.** With no `sec_financials` the precedence
  must collapse to exactly today's behaviour, and the existing T29 tests must
  pass untouched.
- **Do not retune the 90-day constant.** See above; the reason is worth a comment
  at the constant itself.
- The join is by ticker where `sec_financials.ticker` is populated. For delisted
  companies it is NULL, so those rows are reachable only once T51 lands — say so
  in the doc rather than half-joining on names here.

### Tests

- A figure with a `sec_financials` row arrives on its real `filed` date, not at
  period end + 90.
- The same figure with a *restatement* filed later still arrives on the original
  date. This is the look-ahead guard and the most important case.
- No `sec_financials` table → byte-identical to today, asserted against the
  existing T29 fixtures.
- A figure present in `sec_financials` but with an `earnings_calendar` entry

  decide and document — my reading is that the SEC filing date is the harder

## T113 — The form's cashflow block wrote a table the decoder rejects

golden through `backtest.LoadConfigText`; and the smoke render rejects any

## T50 — Refuse (or at least flag) a series the audit calls unusable

**Category:** feature · **Status:** needs-user · **from T41, which measured it**

The audit (T41) found 273 tickers that cannot support a backtest and 1,053 more
whose defects can move a metric on their own. Nothing declines to trade any of
them, and the three worst failure modes are silent:

- **Negative prices** — `VHI` (5,429 bars, to −639.30), `SVA`, `SAFE`, `DEC`. A
  return computed across a sign change is arithmetic nonsense that looks like an
  ordinary extreme move. This one is arguably not a decision at all: no correct
  backtest can hold a negatively-priced instrument.
- **Synthetic flat history** — `HUBB`'s 1,862 consecutive identical closes. A
  moving average over it produces confident output from a series with no
  information in it.
- **Series that are mostly holes** — `MTRA`, 269 bars where the calendar has
  2,613, which (given how `alignToWindow` intersects days) also deletes those
  days for every other holding.

### Why it is yours

Because every option changes results that exist today, and the right severity
is a judgement call:

- **Option A — refuse `unusable`, warn on `suspect`.** A portfolio naming a
  negatively-priced or too-short series fails validation with the reason; a
  suspect one runs and logs. Strongest, and it will break any saved config that
  happens to name one of the 273.
- **Option B — warn on everything, refuse nothing.** Zero blast radius, and the
  warning is easy to ignore, which is how the current silence started.
- **Option C — refuse only the arithmetically impossible** (negative or zero
  prices, fewer than 20 bars) and warn on the rest. My recommendation: it draws
  the line where the data is not merely rough but self-contradictory, and it can
  only break a config that was already producing nonsense.

Whichever is chosen, it must stay **inert when the `data_quality` table is
absent**, like the delisting registry — an unloaded database must behave exactly
as it does today.

Say **"T50: option C"** (or A/B) and it executes: the check in
`validateCoverage`'s neighbourhood, the log lines, the README and `appReference`
updates, and tests that an absent table changes nothing.

## T99 — Nothing says when two portfolios are compared over different windows

**Category:** feature · **Status:** needs-user · **found while answering T98**

Each portfolio genuinely runs over its own `StartDate`/`EndDate` (T98 proves
it). That is the right engine behaviour — a 2010-2015 idea and a 2015-2020 idea
are both legitimate runs.

But the Backtest tab draws them as two lines on one chart and two rows in one
metrics table, which reads as a comparison, and **two return series over
different periods are not comparable**. A 2009-2020 portfolio beating a
2015-2020 one says almost nothing except that it held through the recovery.

`+ Add portfolio` inherits the previous card's window precisely so the default
is a like-for-like comparison, so this only bites when someone deliberately
changes one — which is also exactly when they might not think about it.

### Why `needs-user`

The fix is a judgement call about tone, not code. Options, cheapest first:

1. A note under the chart when the windows differ, naming the spans. Honest,
   unobtrusive, no behaviour change.
2. The same, plus marking the affected metrics columns as not comparable.
3. Refusing the run. **Almost certainly wrong** — running two windows on
   purpose is legitimate and the app should not forbid it.

I would take (1). It needs your call on whether it is worth the pixels, and it
is not the kind of thing to add uninvited to a form you have just started
using.

## T117 — A shipped database cannot be opened read-only, or twice

**Category:** release · **Status:** done 2026-09-06

`InitDB` does a plain `sql.Open("duckdb", path)`, which is read-write
(`src/data/database.go:31`). Both failure modes are reproduced:

API in your head or keep `strategies/README.md` open in another window, and
the only way to find out whether a script worked was to run a whole backtest.

T127–T130 are one idea in four commits: **the editor teaches, the checker
catches, the typo is loud, the error points at the line.** T131 and T132 are
separate ideas and can be dropped without hurting them.

## T127 — The Lua editor does not know the Lua API

## T128 — Check a script without running a backtest

**Category:** feature · **Status:** done 2026-09-06

The TOML tab has ✓ Check; the Lua tab has nothing, so the shortest path from a
typo to knowing about it is a full run. Load the script into a Lua state with
the real globals registered over empty history and report: syntax errors with
line numbers, a missing `step`, a `step` that is not a function, and
`params.x` reads the config never sets. Opens no database and simulates
nothing, like `-check`.

**Done means:** a bound method, a button beside the Lua tab's Save, findings in
the existing console strip, tests for each finding, `README.md`,

**Effort:** medium.

## T129 — A typo in a strategy is a nil, not an error

**Category:** feature · **Status:** done 2026-09-06 · **decided: strict in the
check, never in a run**

`smaa(t, day, 50)` is a call on nil — caught per-day and logged, so it
surfaces. `local x = my_thresold` is silently nil forever, and a strategy that
quietly does nothing looks exactly like one that decided not to trade.

A metatable on `_G` that raises on reading a global that was never declared,
reported as a diagnostic naming the line and the nearest real name ("unknown
name 'smaa' — did you mean 'sma'?"). Scripts assigning their own globals must
keep working, so an assignment declares the name.

**Done means:** the strict mode, every shipped strategy still running clean
under it, a test with a deliberately misspelled global, `README.md`,
`appReference`, and a decision recorded on whether it is opt-out.

**Effort:** medium. **Risk:** it can break a working script that relies on a
nil read; that is why every shipped strategy is part of the test.

## T137 — The app's DuckDB can no longer scan the price table

**Category:** bug · **Status:** done 2026-09-27 — fix 2 chosen by the user: driver upgraded to duckdb-go v2.10505.0 (DuckDB 1.5.x) in 611df79; app binary rebuilt

After `add_collections.py` (delete + reinsert of the `$` series) ran under
**Python DuckDB 1.5.0**, any query that scans `stock_data_optimized` across
tickers fails with `INTERNAL Error: Attempted to access index
9223372036854775807 within vector of size N` in **go-duckdb v1.8.5 (DuckDB
v1.1.3, the app's engine)** and in the **DuckDB CLI v1.3.2**. Python 1.5.0
reads the same queries correctly (10,482 tickers, `$SP500` through
2026-09-25), so the data is intact: 1.5.0 wrote storage structures older
engines cannot read. Single-ticker `WHERE Ticker = ?` reads still work, which
is why the post-load verification (all single-ticker or `LIKE '$%'` queries)
missed it.

Fails: `WHERE Ticker IN (...)` (`src/data/database.go:108`, the backtest
fetch), `GROUP BY Ticker` (ticker list, date ranges), `COUNT(DISTINCT Ticker)`.
Test that shows it: `TestDBOverviewAndQueryTool` (`ui/claude_smoke_test.go`).

**Two ways out — both the user's call:**

1. **Rewrite the file in a format v1.1.3 reads** (no code change), with
   Python 1.5.0, into a NEW file, then verify with the app's engine before
   swapping. Needs ~3.3 GB free:
   ```python
   import duckdb
   con = duckdb.connect()
   con.execute("ATTACH 'stock_data.db' AS src (READ_ONLY)")
   con.execute("ATTACH 'stock_data_v11.db' AS dst (STORAGE_VERSION 'v1.1.0')")
   con.execute("COPY FROM DATABASE src TO dst")
   ```
   Recurs on the next Python write unless (2) is done or the loaders attach
   the same way.
2. **Upgrade the Go driver** so the app reads what the loaders write
   (`github.com/marcboeker/go-duckdb` → a release bundling DuckDB ≥ 1.5, i.e.
   the `duckdb/duckdb-go` v2 line). A `go.mod` change, so it needs the user.
   Durable; the Python loaders then stop being a hazard.

## T50 — Warn on a series the audit calls unusable

**Category:** feature · **Status:** done 2026-09-06 · **Option B, as specified**

The audit found 273 tickers that cannot support a backtest and 1,053 more whose
defects can move a metric on their own; nothing declines to trade any of them.
`VHI` carries negative closes to −639.30, so a return computed across the sign
change is arithmetic nonsense that reads as an ordinary extreme move.

This was `needs-user` because the three options had different blast radii.
**Take Option B: warn, refuse nothing.** A portfolio naming an `unusable` or
`suspect` series emits a diagnostic naming the ticker and the defect; no run
changes its numbers and no saved config breaks. Options A (refuse `unusable`)
and C stay parked — refusing things is a 1.0 decision, made once there is
feedback from people who are not you.

The reason it moved into the beta queue at all: the data now ships with your
name on it, and a stranger will backtest one of the 273 without knowing they
have. `src/data.LoadDataQuality` and `ClassifyQuality` already exist; the
`data_quality` table ships with the database.

**Done means:** the diagnostic (console + CLI), a note in `README.md`, and
`appReference` in `ui/chat.go` so the assistant stops saying nothing checks.
Verdicts are absent when the optional table is — warn once, quietly, and carry
on.

**Effort:** small.

## T99 — Say when two portfolios cover different windows
